## Confirmed hosting direction

Each person has a separate world, with all world generation and simulation running on the user's PC. Browsers display the atlas and send observer controls. Worlds do not interact. This supersedes the specification's original browser-simulation proposal while preserving the observer-only experience.

Each future world must have independent identity, state, configuration/seed, RNG state, clock, command ordering, history, and saves. Reconnecting returns to the appropriate world; another connection attaches to the same simulation. Requests and subscriptions must be checked against the person's access to that world.

**Confirmed lifecycle:** pause and save on departure, restore and resume on return, preserve manual pause, and perform no offline catch-up. These are requirements for future persistent worlds, not behavior provided by the current stateless fixture.

The user authorized proper research and immediate implementation of this baseline. The current modular application provides the HTTP and compute foundation while keeping deployment and installation straightforward.

Ctrl+C closes listeners and workers. [README](../README.md) is the canonical setup, launch, and configuration guide.

## Development reload and verification boundaries

Vite hot updates alone cannot refresh Node's backend or worker module caches. The missing-map incident demonstrated this: an existing process served the new React interface but still returned 404 for its new atlas endpoint. The development supervisor now watches `server`, `shared`, `scripts`, `src/world`, `src/fixtures`, `src/simulation`, the vendored TS/JS runtime and rebuilt `.mjs` artifact, and relevant root configuration files. A 200 ms debounce coalesces saves; SIGTERM invokes the existing bounded shutdown before a replacement process recreates the HTTP host and worker pool. Vite reconnects and reloads the open tab at the same public origin. Browser component/style changes retain Vite hot updates. Invalid host code leaves the application unavailable until corrected; the watcher stays alive to recover on the next edit.

Nodemon is pinned as a development dependency (MIT, compatible with Node 24), uses explicit `node` execution for native TypeScript, and supplies process supervision instead of adding a custom restart manager. Its default TypeScript executable and restart signal are overridden to match Chronicle. Native Node watch-path behavior on this Linux installation differs from its versioned platform documentation, so it was not selected as the portable baseline. [Nodemon configuration](https://github.com/remy/nodemon/tree/v3.1.14), [package compatibility](https://github.com/remy/nodemon/blob/v3.1.14/package.json), [Node 24 watch-path documentation](https://github.com/nodejs/node/blob/v24.20.0/doc/api/cli.md#--watch-path).

New server/core module directories must be included in the watch scopes and exercised by a source-edit regression. Dependency/runtime upgrades and watch-configuration changes require restarting the supervisor itself. Production processes are not watched. Current restarts reconstruct the stateless authored study; a future mutable world requires save/recovery contracts before development restarts can safely discard its process state.

The core watch glob uses the existing `src` parent so a newly created nested `src/simulation` directory remains watched after its first import. Browser regression coverage also checks that writing generated test reports preserves a running review session and its selection.

`npm run check` is the complete implementation-iteration gate: architecture, vendored source/artifact integrity, types, headless tests, build, and Chromium tests against both development and built serving. Browser scenarios use two concurrent Playwright workers against the shared bounded hosts; concurrency does not inherit the machine CPU count. The GitHub workflow runs the same command with the pinned Node and lockfile and retains failure artifacts. Tests for live updates copy actual application source into temporary projects and share only installed dependencies; their file edits never reach the running user lab. They verify behavior through the real worker, HTTP, proxy, and browser paths, including recovery and cleanup. Keep tests aligned with new behavior and connections as the project grows. A passing fresh-server suite alone does not establish that an existing review session has updated.

## Seeded geography and bounded detail delivery

The default browser scenario is the seeded annual-climate preview. `src/world/generation/` contains deterministic noise, continent/island elevation, climate, sparse resource sites and encoding. The worker is the only runtime application layer importing generation. Browser, renderer and HTTP imports of this directory are rejected by Biome and exercised by negative architecture tests. The directory and vendored runtime are watched; climate-only and vendor-only source-edit regressions verify that changes replace workers and invalidate cached generation at the same proxy origin. Browser, renderer, shared, HTTP and unrelated core modules also cannot import the vendored runtime directly.

World generation protocol 4 is independent of authored atlas protocol 3. `shared/generated-world.ts` specifies settings (seed plus standard/large resolution), generator version, immutable geography identity, a manifest, and 128 × 128 tiles. Numeric columns carry elevation in metres, temperature in tenths °C, moisture in thousandths, biome codes, resource codes (zero means no site), and fertility scores (0–100). Manifest and tile validators check shape, lengths, ranges, water/elevation consistency, identity, tile coordinates and summary accounting before publication/use. Row-major cell IDs remain stable within an identity. There are no province, country, settlement or occupation fields in this geographic contract.

Both presets cover 510 million km² including ocean. Standard has 512 × 256 cells; large has 1,024 × 512. Equal-area cylindrical latitude is `asin(1 − 2v)`, with horizontal wrapping and bounded poles. Cell areas are uniform, while apparent map lengths and shapes are distorted near the poles. Future travel mechanics require geodesic or explicit land-travel distances; rendered cell edges are not uniform ground lengths. Resolution is not a separate planet area setting in this preview.

Generator 5 uses a pinned, patched [Mindwerks Platec](https://github.com/Mindwerks/plate-tectonics) C++ core compiled with Emscripten 6.0.5 to a committed WebAssembly/ESM artifact under `vendor/platec/`. A fresh module instance owns each asynchronous job; raw heights are copied and validated before destruction. The WASM heap is capped at 128 MiB and simulation at 2,500 steps, inside the existing disposable worker deadline. This heap cap is separate from V8/process memory. Complete source, licenses, local patches, compiler options and checksums are retained; `npm run check:tectonics` rejects source/artifact drift, and explicit `npm run build:tectonics` rebuilds it. Ordinary installation and startup need only Node and npm.

Both atlas presets refine one fixed 512 × 256 tectonic base, preserving geography across resolution changes. Initial continental noise uses all 32 seed bits and a larger domain to support several crust cores before movement/collision. The adapter treats the toroidal model as an elevation donor: it chooses an ocean-heavy cut and trims about 1% of donor rows from each side, then samples bounded latitude while keeping longitude periodic. A separately interpolated donor land/water mask preserves straits during elevation refinement. The outer 3% of atlas rows fade into separate polar oceans. Dimensionless crust thickness becomes bounded metre elevations with deterministic local relief. Broad lowlands and coastal relief grading feed the existing climate pipeline. This is an artistic tectonic approximation, not spherical geological or drainage simulation.

The climate is a reproducible annual approximation: a symmetric latitude baseline and elevation cooling, broad moisture bands, ocean replenishment, finite wind transport, moisture loss on rising slopes, and a terrain-weighted crosswind averaging of annual moisture. The crosswind step prevents independent latitude rows from producing narrow humidity stripes downstream of small coastal differences. Biomes follow those values rather than per-island quotas. Sea ice is a cold-water classification; snow is a land biome. Seasonal water balance, weather, ocean currents and calibrated geology remain future stages. Resource sites use suitable terrain and sparse spacing across the longitude seam, with independent rarity choices; extraction remains catalog metadata only.

Hydrology runs after climate and before final lake biomes/resources. `src/world/generation/hydrology.ts` uses deterministic Priority-Flood over D4 neighbors (horizontal wrapping, bounded poles), routes each lake to one outlet or closed root, and accumulates moisture-weighted cell area in topological order. Ocean is negative-bed water connected to polar boundaries; enclosed negative-bed water remains at level zero. New lakes are supply-limited, at most 20 m deep and 100,000 km²; deep or oversized depressions retain a bounded pond near their minimum instead of flooding the accepted continents. All passes are bounded, elevation remains unchanged, and unsupported configurations fail explicitly. This static retention approximation does not simulate erosion, groundwater or seasonal discharge.

`shared/world-hydrology.ts` validates the authoritative sparse river graph, lake membership/levels/outlets, and explicit dry sinks. Ordinary river channels require accumulated runoff of at least 5,000 area-index units. Weaker lake outflows retain their full downstream path to ocean, another lake or a registered dry terminal with incoming flow below that threshold. The contract rejects broken paths, uphill edges, cycles, contradictory lake geometry, impossible incoming/terminal flow and submerged land resources. The renderer and inspector consume this same graph. Open lakes and rivers expose mapped freshwater access; closed-lake salinity is not inferred. Lake surface shading uses water level while inspection preserves bed elevation. The Rivers toggle affects the Biomes layer; temperature/moisture views retain literal climate colors. `src/renderer/river-paths.ts` derives connected reaches once from the validated graph, retaining every edge and exact fork/water-boundary positions. Quadratic bends stay within routed cells; longitude is unwrapped before smoothing. Reach runoff controls width and zoom-dependent visibility, keeping larger rivers at overview and revealing small streams at detail. This is presentation only: generation identity, cell picking and water facts are unchanged.

The worker validates and pre-encodes a full-resolution terrain surface, a 256 × 128 sampled climate overview and all detail tiles into an immutable bundle. The terrain surface packs signed little-endian 16-bit elevation followed by an unsigned 8-bit biome for each row-major cell, base64 encoded in JSON. It preserves narrow coasts and small islands at overview zoom without fetching every tile. Surface validation checks exact dimensions, byte length, value ranges, water/elevation consistency, full biome counts and agreement with sampled terrain values. Each received detail tile must also match the surface elevation and biome for every cell. Private decoded validation data is retained weakly per manifest, avoiding repeated whole-world decoding for each tile. `server/generated-world-store.ts` retains at most two bundles, including unfinished jobs. It shares in-flight generation for identical settings, evicts only completed least-recently-used entries, removes failed entries for retry, and cancels unfinished work only after its last waiting observer disconnects. Closing the app cancels unfinished generation and clears the cache. This is a disposable geography cache, not saved user worlds. The main thread unpacks bounded bundle strings and validates the manifest; generation and tile encoding stay in workers.

The browser receives the full terrain surface and sampled climate overview first and requests exact detail for visible tiles or selected cells. Its client caps requests at four concurrently and its data cache at sixteen tiles. Current viewport tiles are protected from eviction by late offscreen responses; protection moves with the view and clears at overview. The biome renderer uses one full-resolution terrain plate and world-coordinate wave, vegetation, dune and crag marks at several zoom levels. It samples relief across world/tile boundaries and keeps biome terrain identical as detail arrives. Climate layers use their literal legend colors, with detail textures bounded to retained tiles and cleared when changing layer. World replacement cancels the prior client; revision checks prevent late data from changing selection or replacing a newer world. Failed replacement keeps the displayed world; failed detail keeps the overview and requires an explicit retry. Cell inspection reads a full-resolution tile even when the map is showing an overview. Pan, zoom and inspection are observer views, not world mutations.

Fertility is generated after geography, climate, hydrology and resources, without modifying those fields. `shared/fertility.ts` is a pure game model shared by worker generation, transport validation and exact cell inspection. Its context indexes lake levels and freshwater/river proximity once per surface. Regional slopes use neighboring surface elevations and spherical distances in the equal-area projection, with wrapped longitude and bounded poles. This is coarse regional relief, not local field slope. Estimated soil classes use terrain, climate and nearby rivers; actual soil chemistry, geology and crop requirements are not known. Water is excluded. Rounded warmth, moisture, soil, slope and drainage factors multiply into an integer score, so the inspector explains the transported value exactly. Freshwater proximity is descriptive and grants no irrigation. Manifest samples and every tile score are checked against this same rule. Only one extra numeric column is transported; explanatory factors are computed for inspected cells. The full-resolution terrain encoding and water graph remain unchanged. Generator 5 / protocol 4 invalidate older generated cache identities; authored protocols stay unchanged.

## Legacy identity initialization

Civilization 01 composes one initial identity/location snapshot alongside geography in the existing disposable worker. `src/world/civilization.ts` evaluates eligible land using existing fertility, temperature and mapped freshwater; ties use a seeded hash. Naming and a curated color palette use independent seed salts. `shared/civilization.ts` defines protocol 1 / spawn 1 and validates identity, cardinality, bounded name/color/cell fields, matching world identity and a suitable land biome. The worker's `WorldStudyBundle` contains the unchanged generated-world manifest/tiles plus a separately encoded civilization response (8 KiB maximum). The complete bundle still has its 20 MiB cap. `GET /api/world/civilization` shares the existing two-entry cache, compute job, response admission and cancellation. Browser/renderer/HTTP imports of the creation module are prohibited by the architecture check and its negative scenarios.

The current browser does not fetch or display the legacy snapshot. Fresh geography has no political identity marker. Only a validated begun/restored tribal view supplies the marker, Locate control and camp identity inspection. Markers appear on Biomes with labels, contrasting outlines and CSS-pixel picking; climate/fertility layers retain their numeric meaning. The sidecar remains an internal initialization/compatibility contract for existing naming and saved tribal IDs, not an already-established civilization.

This is immutable initialization, not resident simulation state or a persistent user-world ID. `civilization-1` is scoped to the preview world. A founding marker makes no province, settlement, population, claim or military-control assertion; no default tick runs. Introducing those mechanics will require the agreed capital/province relationship and explicit accounting contracts. The user wants one tribe's growth and decisions developed first; civilization is a later stage, and inter-group systems remain later work.

## Retained regional atlas and module ownership

Verdant Reach is a deterministic **authored regional study** with a bounded 320 × 200 topology. Its 64,000 square cells each cover 4 km², giving 256,000 km² in total. The study contains several substantial landmasses and a southern archipelago, eleven biome types, eleven resource types, and 77 connected unclaimed provinces. Its fixed elevation and climate fields produce coherent regions for atlas evaluation; they do not establish a user-seeded planet generator or a complete drainage/climate model.

Every cell has a stable row-major ID, integral elevation in metres, a biome, an optional resource site, and a nullable province ID. `resource: null` means no special site, not zero biome productivity, an undiscovered resource, or depletion. The version-2 fixture distributes a few hundred terrain-appropriate sites with spacing; gold and uranium are rarer than common resources. Ocean and shallow-coast cells have negative elevation and no province. Every land cell belongs to one connected province. A province's nullable `countryId` is a separate hierarchy link; the initial country list is empty. Resource presence is neither an inventory nor an extraction/production rate. Camera movement, layers, and selection do not modify world data or ownership.

| Module | Responsibility |
|---|---|
| `shared/atlas.ts` | Protocol-3 world, cell, biome, nullable resource, province, country, and annotation schemas/types; dimension, identity, reference, water/land, and province-connectivity validation |
| `shared/terrain.ts` | Retained protocol-1 Aster terrain contract |
| `shared/studies.ts` | Authored-study identifiers and seeded-world settings for disposable compute jobs |
| `src/fixtures/verdant-reach.ts` | The actual shared regional fixture, deterministic resource assignment, and connected province construction |
| `src/world/atlas.ts` | Biome/resource display catalogs and atlas/province summaries derived together in one cell pass |
| `src/world/resources.ts` | Renewable/mineral site kinds and required extraction technology, independent of visual styling |
| `server/workers/terrain-worker.ts` | Construct the selected authored or generated geography, validate its matching contract, and encode bounded JSON |
| `src/api/atlas.ts` | Request the atlas and validate the response before rendering |
| `src/components/RegionalAtlas.tsx`, `src/components/AtlasCanvas.tsx` | React loading/reset state, legends, layers, province/cell inspectors, controlled selection, and renderer lifecycle |

| `src/App.tsx`, `src/components/LegacyTerrainLab.tsx` | Select the generated-world default, Verdant at `?scenario=verdant`, or Aster at `?scenario=aster` |

Annotations and site positions belong to fixture data. The resource layer and inspector read actual site presence; ordinary cells explicitly show no resource site in that cell. Province totals are derived once per received world, independent of display filters/layers, and exclude water cells without a province. Extraction requirements are catalog metadata displayed for review, not a claim that an actor knows a technology or can currently produce goods. The preview shows all sites; research, discovery, production, labor, and stocks need later contracts. The hierarchy inspector displays real references, including unclaimed land and water without a province. Future sovereignty, occupation, habitation, and lifecycle operations still need their own mechanics and contracts.

Selection is explicit view state: none, a province ID, or a cell ID. The first land click selects a province and displays its totals; another click inside selects a cell and displays only its local details. Clicking that same selected cell returns to its province; clicking a different cell in the active province moves cell selection. Province tint and cell outline are mutually exclusive. Crossing into another province restarts at province level; water opens directly and stays at cell scope on repeated clicks. Back/Escape navigate up, and successful replacement clears selection while failed replacement retains it. The renderer keeps a separate keyboard focus cell, preserving exact-cell arrow navigation and enabling Enter/Space activation through the same cycle. Pure selection transitions are shared by the renderer and inspector; neither changes the authoritative world. Country-level selection remains future work.

## Agreed province design awaiting implementation

The user approved country-created provinces on 10 September; [specification §§3–4 and §9](CHRONICLE_SPEC.md) define the intended behavior. A founding settlement is both national capital and first provincial capital. Additional provincial capitals organize territory; ordinary towns support population and resource extraction. Initially unclaimed game-world cells have no political province. Successful hostile capture of the designated provincial capital immediately transfers the whole province's sovereignty; uncaptured cells can remain under opposing military control. Province identity and local population/resources survive the transfer.

This requires a later versioned world contract: protocol 3 currently requires every land cell to belong to a province and has no settlement, capital, or military-control data. The existing 77 unclaimed groups remain part of the authored test fixture; they do not implement country-created provinces. Future contracts must distinguish unassigned land, settlement roles, province membership/sovereignty, and cell military control. Creation, membership changes, capture transfers, and splits/mergers need canonical operations and accounting tests. Exact initial claim size, growth and relocation costs, and lifecycle rules remain scoped design work; do not infer them from the current fixture or silently weaken its validation.

## Growth and dependency decisions

Chronicle is intended to become a substantial simulation project. Small slices govern delivery and review; they do not limit the product's architecture or expected complexity. Plan for large world datasets, many active and archived entities, long histories, and multiple independent worlds. Evaluate memory residency, generation and stepping costs, history retention, simultaneous saves, and reconnect payloads with representative workloads as those capabilities develop. The current fixture and conservative runtime limits are evidence about the present workload only, not eventual capacity targets.

Keep one modular application now, with clear boundaries between world rules, transport, HTTP, compute ownership, rendering, and persistence. Those boundaries must allow later changes to process placement, server topology, and storage when known requirements or measurements justify them. Changes still require explicit contracts, implementation, migration planning, and verification; modularity does not make a database or distributed-runtime migration automatic. Evaluate additional runtime services by the requirements they satisfy and their operating costs, rather than assuming either that the project is too small to need them or that growth alone requires them immediately.

Use established libraries and tools for infrastructure where they provide a concrete benefit. The user authorizes necessary local package/tool installation for current work and future growth without an extra approval step. For adoption, check purpose, maintenance, license, Node/TypeScript and browser compatibility where relevant, operational requirements, and the cost of integration or replacement. Verify actual behavior with the installed version, pin direct package versions, update the lockfile, and reproduce installation with `npm ci`. Keep README accurate and preserve `npm ci`, then `npm start`, as the everyday setup and launch path.

`npm run check:architecture`, included in `npm run check`, runs the targeted Biome rules over `src`, `shared`, `server`, `scripts`, and the authored `vendor/platec/runtime.ts` helper. The configured boundaries keep shared contracts independent of application layers; world/fixture/simulation modules independent of rendering, React, and host infrastructure; renderer and browser code out of host computation; HTTP modules out of direct fixture/simulation execution; and worker handlers out of HTTP orchestration. Node module imports are rejected in the browser, renderer, shared contracts, world core and authored vendor helper. That helper may import only its local generated `platec.mjs` module; it cannot depend on Chronicle application layers. Generated C++/ESM files remain outside Biome and are covered by artifact-integrity checks. Import cycles, including type-only cycles, and undeclared package dependencies are also checked. Formatting and general style rules are not enabled by this configuration. [Configured rules](../biome.json), [Biome import restrictions](https://biomejs.dev/linter/rules/no-restricted-imports/javascript/), [cycle checking](https://biomejs.dev/linter/rules/no-import-cycles/javascript/)

Runtime modules also reject development-only package imports; composition scripts retain permission to load development tools such as Vite. These are static import checks, not complete runtime isolation. Literal import paths can be checked, but computed module names, worker URLs, access to browser/Node globals, and architectural intent still need review and appropriate tests. Update the rules when adding layers or import conventions, and retain independent review plus headless, browser, and process tests. Passing this check alone does not establish deterministic simulation or valid save/lifecycle behavior.

## Transport and capacity boundaries

Map endpoints have separate versioned contracts and use `Cache-Control: no-store` for HTTP responses:

| Endpoint | Payload | Browser study |
|---|---|---|
| `GET /api/world` | Generated-world protocol-4 manifest and overview | Default generated geography |
| `GET /api/world/tile` | Generated-world protocol-4 exact detail tile | Requested as needed by the default view |
| `GET /api/atlas` | `{ protocolVersion: 3, world: AtlasWorld }` | Verdant Reach at `?scenario=verdant` |
| `GET /api/terrain` | `{ protocolVersion: 1, world: TerrainWorld }` | Aster Island at `?scenario=aster` |

Workers construct geography, validate the matching contract, and serialize its JSON. The browser checks the shared structural and semantic contract before rendering. Invalid replacement data or failed requests preserve the last valid map. Each full-fixture payload remains limited independently to **100,000 cells** and **8 MiB of JSON**. Generated-world manifests are capped at **4 MiB**, detail tiles at **512 KiB**, and worker bundles at **20 MiB**; the browser does not fetch the complete bundle.

Protocol 3 explicitly changes the cell resource contract to a resource ID or null. The worker uses the shared protocol constant; the browser rejects older envelopes instead of silently interpreting them. Fixture version 2 records the changed site layout. There are no saved-world migrations in this stateless lab; future persistence must version and migrate resource state separately.

All map endpoints share one pool: two workers, or one when only one processor is available, with four waiting jobs and a twenty-second deadline that includes queue time (configurable up to twenty-five seconds, below the thirty-second browser request deadline). Total admitted map responses across the routes are bounded to worker count plus queue allowance, with admission retained until the response finishes or closes. This also constrains work retained for slow clients after computation completes. Generated-world cache admission also limits simultaneous uncached seeds to two. Configuration is validated on startup; defaults and allowed ranges are recorded in README.

Request parsing, sockets, deadlines, and compute admission have explicit limits. Overload and timeouts return retryable failures. Disconnect cancels disposable terrain work; worker failure returns an error and does not fall back to computing on the HTTP thread. Structured logs and server-generated request IDs support diagnosis. `/api/health` establishes HTTP responsiveness; `/api/ready` reports worker/admission diagnostics and returns 503 when busy or unavailable. Startup exercises the actual worker path before announcing readiness.

These are conservative engineering defaults. Worker heap limits and payload bounds are not a total process-memory guarantee. `npm run bench:backend -- --atlas` measures the Verdant Reach pipeline; `npm run bench:backend` retains the Aster baseline. Each records configuration, hardware, latency, request outcomes, event-loop delay, and memory observations. Fixture measurements do not establish simultaneous-world capacity, procedural-generation performance, or simulation speed. Actual measurements and checks belong in the relevant feature brief.

## Tribal world execution

Tribe 01 adds a separate, long-lived simulation/storage worker. The terrain pool still runs disposable jobs: cancelling a Piscina task must not cancel the authority for a mutable world. `src/simulation/tribe.ts` owns pure creation/reset/daily stepping; `shared/simulation.ts` owns versioned checkpoint and view contracts. React and the renderer consume views, and HTTP routes pass commands to the worker. SQLite imports are explicitly banned from HTTP orchestration and all browser/core modules.

The worker serializes mutations for each independent UUID instance. Geography is identified separately by seed, size and generator version. A placement seed samples eligible cells; immutable preview identity is not mutable simulation identity. State carries protocol/rules versions, instance ID, reset incarnation, monotonic revision, completed days, RNG state, camp/tribe population and requested run/speed. Reset changes incarnation; stale incarnation commands always fail with 409. Step/reset/play/speed also require the current revision. Idempotent Pause accepts an older revision within the same incarnation, so a concurrent tick cannot prevent stopping the clock; future revisions are rejected. Clients read current state after conflicts before another user-directed attempt. A failed command response is never automatically replayed as a second step.

POST `/api/simulation/open`, `/observe`, `/command` and `/release` use bounded shared schemas. A missing instance is initialized using the existing bounded geography cache; reopening a version-2 saved instance uses its persisted settlement environment without regenerating it; opening a legacy version-1 instance first obtains matching geography for explicit migration. The browser still loads terrain for display. Mutable checkpoint/view transport is bounded at 8 MiB and does not repeat geography; current settlement payloads are much smaller. `GET /api/ready` reports simulation status separately from terrain readiness, allowing geography to remain usable if saves are unavailable.

Current defaults: at most 16 resident instances, 64 observers per instance, 64 pending small RPCs and 2 pending geography initializations. A 1-second scheduler advances one bounded batch per eligible world, using the same daily steps as manual advancement; supported speeds are 1 or 10 days per batch. Delayed scheduling does not accumulate catch-up batches. One observer does not allocate one worker. These are safeguards for this initial workload, not capacity promises for future populations and histories. Additional workers/shards require measured scheduling and ownership changes.

## Persistence and lifecycle

The browser remembers the selected game instance separately for each geography. **New game** replaces that reference with a fresh UUID and history seed before opening the new host instance. It immediately invalidates the old response stream and clears rendered simulation state; observer cleanup releases the former instance without deleting its checkpoint. Failed creation retries the recorded new identity, while failed local-storage writes leave the prior reference/state untouched. Refresh resumes the selected replacement. **Reset simulation** replays its existing identity; geography regeneration does not itself create a new history.

Tribe 01 uses Node 24's built-in `node:sqlite` in the dedicated worker. This reassesses Backend 02's provisional SQLite choice against the current small checkpoint workload: no server installation, atomic local writes, explicit schema versions and bounded state. The Node API is release candidate; the supported runtime is pinned and tested. SQLite uses WAL with `synchronous=FULL`. A committed transaction publishes a complete candidate state while retaining the previous payload; only then does memory/the response advance. SQLite WAL checkpoint housekeeping is distinct from a simulation checkpoint and uses SQLite's normal auto-checkpointing.

The save directory contains `simulation.sqlite` (current/previous checkpoints) and `simulation-owner.sqlite`. A lifetime exclusive transaction on the separate owner database rejects a second simulation host for the same directory. OS locks release after process death. Mutable state lives separately from disposable geography, and every completed batch is durable rather than depending on a shutdown-only save. Invalid/unsupported state is rejected and retained; migration is explicit. Transaction failures preserve the prior checkpoint, suspend ticks and retain recoverable resident state. An explicit successful save/pause command recovers after storage is repaired. A completely failed disk cannot persist a new failure flag; after restart only the last durable checkpoint is available.

The browser renews observer leases through nonoverlapping polling and sends an independent release on departure. Last release stops work immediately; a missing release expires after 30 seconds including reconnect allowance. Once no observers remain, already-saved state can leave memory. Saves retain requested running versus manual pause, so only a previously running instance resumes when an observer returns. Offline wall time is never simulated. Browser local storage remembers UUIDs per geography/placement seed; this is a local lab reference, not a user account or remote authorization.

Default saves live in `.chronicle/`, outside Git, watchers and static serving. `CHRONICLE_DATA_DIR` chooses another local directory; `public/` and `dist/` paths are rejected, including resolved symlink ancestors, and direct built-server configuration rejects a save directory beneath its static root. Stop the host before copying/restoring the entire directory (including any SQLite sidecars).
