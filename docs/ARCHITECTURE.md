# Chronicle architecture decisions

Updated 1 October 2026. Chronicle is the seeded generated-world page (generator 6 plate-generated continental geography, global annual climate, biomes, rivers and lakes, natural fertility and sparse resource sites, with bounded delivery to the browser) plus the civilization simulation that [VISION.md](VISION.md) defines, built milestone by milestone in a dedicated host worker; see [Simulation runtime](#simulation-runtime). This geography is visually accepted; see [Worldgen 01](features/worldgen-01.md), [Hydrology 01](features/hydrology-01.md) and [Fertility 01](features/fertility-01.md). At the user's request, the civilization runtime (its simulation/storage worker, saves and civilization identity), the authored regional atlas study and the original terrain lab were removed; the local branch `archive/civilization-v1` keeps them as reference only. [Dev 01](features/dev-01.md) records automatic restarts and the complete regression gate. [Backend 02](features/backend-02.md) retains the foundation's evidence; [BACKEND_RESEARCH.md](BACKEND_RESEARCH.md) records the 9 September 2026 backend research; its persistence, storage and scheduler proposals predate [VISION.md](VISION.md) and do not bind it.

## Confirmed hosting direction

Each person has a separate world, with all world generation and simulation running on the user's PC. Browsers display the atlas and send observer controls. Worlds do not interact. This supersedes the specification's original browser-simulation proposal while preserving the observer-only experience.

Each future world must have independent identity, state, configuration/seed, RNG state, clock, command ordering, history, and saves. Reconnecting returns to the appropriate world; another connection attaches to the same simulation. Requests and subscriptions must be checked against the person's access to that world. Until user accounts exist (not part of the VISION.md run), the local user is the only person and has access to every world; VISION.md's world-instance identity defines a world.

**Confirmed lifecycle:** pause and save on departure, restore and resume on return, preserve manual pause, and perform no offline catch-up. These are requirements for future persistent worlds, not behavior provided by the current stateless geography.

|---|---|---|

| Development supervision | Nodemon 3.1.14, configured in `nodemon.json` | Restart the combined application after host/core edits, including changes used only by worker imports |

The user authorized proper research and immediate implementation of this baseline. Fastify replaces the first slice's native HTTP routing; a bounded worker pool replaces synchronous fixture construction on the request thread. The current modular application provides the HTTP and compute foundation while keeping deployment and installation straightforward.

`npm start` runs the nodemon supervisor around `scripts/start.ts`, which launches Fastify and Vite in one Node application process with worker threads for CPU work. The development backend binds to an automatically assigned loopback port; Vite proxies `/api` through the browser origin at port 5173. `npm run build`, then `npm run serve`, starts the built frontend and API together on port 4173 through Fastify without Vite or nodemon. `npm run preview` aliases that built-app mode. Ctrl+C closes listeners and workers. [README](../README.md) is the canonical setup, launch, and configuration guide.

## Development reload and verification boundaries

Vite hot updates alone cannot refresh Node's backend or worker module caches. The missing-map incident demonstrated this: an existing process served the new React interface but still returned 404 for its new map endpoint. The development supervisor now watches `server`, `shared`, `scripts`, everything under `src/world` and `src/simulation`, the vendored runtime and rebuilt `.mjs` artifact under `vendor`, and relevant root configuration files (`vite.config.ts`, `tsconfig.json`, `package.json`, `package-lock.json`). A 200 ms debounce coalesces saves; SIGTERM invokes the existing bounded shutdown before a replacement process recreates the HTTP host and worker pool. Vite reconnects and reloads the open tab at the same public origin. Browser component/style changes retain Vite hot updates. Invalid host code leaves the application unavailable until corrected; the watcher stays alive to recover on the next edit.

Nodemon is pinned as a development dependency (MIT, compatible with Node 24), uses explicit `node` execution for native TypeScript, and supplies process supervision instead of adding a custom restart manager. Its default TypeScript executable and restart signal are overridden to match Chronicle. Native Node watch-path behavior on this Linux installation differs from its versioned platform documentation, so it was not selected as the portable baseline. [Nodemon configuration](https://github.com/remy/nodemon/tree/v3.1.14), [package compatibility](https://github.com/remy/nodemon/blob/v3.1.14/package.json), [Node 24 watch-path documentation](https://github.com/nodejs/node/blob/v24.20.0/doc/api/cli.md#--watch-path).

New server/core module directories must be included in the watch scopes and exercised by a source-edit regression. Dependency/runtime upgrades and watch-configuration changes require restarting the supervisor itself. Production processes are not watched. Current restarts regenerate stateless geography and discard the disposable generation cache. Until [VISION.md](VISION.md) slice P adds save and resume, a restart (including a development reload) resets the simulation to year 0 and the lab says so; from slice P a restart resumes from the last save.

The recursive `src/world/**/*` glob keeps a nested directory created after startup watched after its first import; a source-edit regression covers this. Browser regression coverage also checks that writing generated test artifacts preserves a running review session and its selection.

`npm run check` is the complete implementation-iteration gate: architecture, vendored source/artifact integrity, types, headless tests, build, and Chromium tests against both development and built serving. Browser scenarios use two concurrent Playwright workers against the shared bounded hosts; concurrency does not inherit the machine CPU count. The GitHub workflow runs the same command with the pinned Node and lockfile and retains failure artifacts. Tests for live updates copy actual application source into temporary projects and share only installed dependencies; their file edits never reach the running user lab. They verify behavior through the real worker, HTTP, proxy, and browser paths, including recovery and cleanup. Keep tests aligned with new behavior and connections as the project grows. A passing fresh-server suite alone does not establish that an existing review session has updated.

## Simulation runtime

Built from [M0](features/m0.md) on, following VISION.md's architecture section.

- **Worker.** Each live world's simulation runs in its own long-lived `node:worker_threads` worker (`server/workers/simulation-worker.ts`), not in the Piscina geography pool. `server/simulation-host.ts` creates it on the first observer request for a world, passing the bundle exactly as the generated-world store serves it (manifest and tile JSON); the worker validates both with the shared parsers before deriving regions. At most `CHRONICLE_SIMULATIONS` (default 2) simulations live at once; beyond that the least recently used one stops and starts again at year 0 when next requested. A crashed, hung (no reply within 10 s) or stopped worker is terminated and replaced the same way; requests in flight get 503, and concurrent observers share the one replacement. A world whose simulation fails to start is refused for 30 s instead of being rebuilt on every poll. Each worker reports a fresh `runId`, and each manual reset increments the frame's `epoch`, so every observer can tell a restart or a reset from a continuing history. Choosing another seed in a lab tab resets the newly chosen world to year 0; opening the page attaches without resetting.
- **Clock.** One tick is one month. The worker plays in slices of at most 40 ms (`CLOCK_TUNING.sliceMs`), yielding between slices so frame requests and controls stay responsive. Speed presets are 1 month, 1 year and 10 years per second and as fast as possible; run to year plays at full speed and pauses at January of that year. Controls are applied in arrival order.
- **Systems.** `src/simulation/` holds the rules: the twelve systems run in VISION.md's fixed order every month (`SYSTEMS` in `state.ts`), each with its own seeded RNG stream per tick (`rng.ts`: a hash of root seed, tick, system id and optional entity id), so adding a system or a draw never shifts another. Longer cadences select the entities due in a month by id. Per-system wall-clock time is accumulated for the study but never affects results. Tunables live in typed data (`tunables.ts`) and are validated before a simulation starts. `SIMULATION_RULES_VERSION` (in `simulation.ts`) and `REGION_PARTITION_VERSION` (in `regions.ts`) are part of the world-instance identity (`sim-<rules>.<partition>:<worldKey>:<seed>`); every slice that changes rules or tuning bumps the first.
- **Regions.** `regions.ts` partitions land cells deterministically from the validated geography: weighted Poisson-disk seeds favouring fertile, watered land; capped multi-source Dijkstra on terrain movement cost over true ground lengths; then repair so every region of a landmass larger than one region lies within 20,000–60,000 km² (merge into a neighbour when it fits, otherwise take border cells from neighbours that stay in range and connected). Landmasses below the minimum stay single island regions. It precomputes water (coast, open-lake access, river tier from runoff thresholds), assigned resource sites (land sites plus fish within 2 cells of a coast or lakeshore), defensibility, land neighbours with travel cost and crossed river tier, sea crossings up to 900 km and ranked settlement sites. Neither `src/simulation` nor the simulation worker imports `src/world/generation` (Biome rules with negative tests).
- **Bands and food** ([M1](features/m1.md)). `food.ts` derives per-region labour capacity and yield for foraging, hunting and fishing from the validated geography; output saturates with labour and workers fill methods to a common marginal yield; capacity is solved as the population whose output equals its need. `bands.ts` holds spawning, the production system (food, perishable stores, game depletion and regrowth) and the population system (births and deaths from food security, yearly moves and splits with recorded causes). People are integers with fractional carries; food is counted in integer units of 1/100 person-month, so the per-tick accounting invariants are exact. A polity (a tribe, later a civilization) holds one population group in each of its regions — a band, later a village — with a heartland group; at most one group lives in a region. A split usually adds a band to its tribe and sometimes, graded by distance from the heartland, the tribe's size and its culture, founds a tribe of its own. `observer.ts` builds what frames carry for the lab: polity markers, villages, the population series and a region's details on request.
- **Knowledge and settling** ([M2](features/m2.md)). `techs.ts` holds the tech graph as data (63 techs, Stone to Atomic: prerequisites, costs, tags, environment affinities and effects limited to coefficient multipliers, food methods, resource reveal / extraction / use, mobility and unlocks), validated at worker startup together with the `RESOURCE_RULES` extraction names. `knowledge.ts` derives each polity's multipliers, methods, mobility, era and available techs from its known set and chooses research targets by weighted random (need, environment, exposure, culture, effort); `research.ts` is the knowledge system (yearly contacts within two regions, monthly research, discoveries with causes, diffusion through exposure); `deposits.ts` gives each deposit's unknown / known / usable state per polity. `food.ts` adds herding and farming with river and lake multipliers, a harvest calendar by latitude and the sowing choice (crops valued against the store that must last until the harvest); `bands.ts` adds crops in the field (sown monthly, brought in at the harvest, with their own ledger), specialists (settled polities only), sea crossings with Sailing or Navigation and settling a whole tribe into one civilization that owns all its regions, with a named village in each and the capital in its heartland. Research is per polity: a tribe's base research comes from its people up to one community's size, its specialists add to it, and its environment weights are graded by the share of its people on each kind of land. Research discoveries take effect after the month's loop, so knowledge moves one contact a month. Invariants also check the home-landmass rule before Sailing, the crops ledger, ownership and capitals every tick.
- **Knowledge of the world** ([M3.1](features/m3-1.md)). `perception.ts` keeps each polity's map: per region unknown, known (a snapshot of its occupant and owner when last seen) or observed (its own regions, their land neighbours and the sea crossings it can reach), rebuilt when the polity's regions or sea reach change and yearly. Civilizations remember regions that leave their sight; tribes keep only what is in sight. Two polities meet (mutually, one `firstContact` event per pair) when one sees where the other lives; a breakaway inherits its parent's contacts. Once a year a civilization learns what each polity in its sight sees. Research contacts are polities within two regions that it has met. It is also the query layer: physical systems may read the true world; decision code receives only the view `decisionView` builds.
- **Decisions and expansion** ([M3.2](features/m3-2.md)). The decisions system (`decide.ts`) runs every six months per civilization (staggered by id): `perception.ts` builds the civilization's view (its needs, its candidate land with value, crossing cost and travel-km from its capital, and the unknown land next to its sight), `decisions/choose.ts` scores Expand, Explore and Do nothing and picks by weighted random among the best three, and the step is logged with every option's factors. `decisions/` may import only the view types, tunables, the RNG and its own folder (a Biome rule with negative tests). `expansion.ts` carries the choice out in the true world: settlers found a village, or a tribe's band there is taken in (`transferGroup`) or moves on to land that feeds it; expeditions reveal land and meet its people. Governance reach is a base times the techs' reach multiplier, in travel-km (edges' travel-km plus river crossings, sea crossings by distance). Migration (population system, yearly per civilization) moves people between populated civilization regions by their difference in land pressure. `scenarios.ts` is a labelled test fixture (one civilization alone on the largest landmass).
- **Joining and stability** ([M3.3](features/m3-3.md)). A farming tribe that settles (more likely the more people it has) first weighs joining a civilization next to it: `perception.ts` builds its view (`joinView`: met civilizations whose land it sees, with kinship, culture similarity from `culture.ts`, the people it sees there, their food and stability, the cheapest crossing), `decisions/join.ts` weighs each against founding its own, and the civilization admits it by its governance reach; the tribe's bands pass to the civilization (`transferGroup`), each with a village. The stability system (`stability.ts`, yearly per civilization) rates each region from hunger, distance beyond reach and foreign rule; unrest (below a threshold, with hysteresis) lowers output in production and specialists' research. `causes.ts` turns factors into event causes for every system.
- **Chronicle and invariants.** Systems emit structured events; the chronicle system flushes them at the end of the tick, assigning ids in system order and keeping a running hash of the log for determinism checks. `invariants.ts` checks every tick (ordered, valid events; non-negative values; exact population and food accounting per region and band, with migration and carried food closing across them) and the partition once (every land cell in exactly one region of its landmass, contiguous, within the area range unless an island). Wealth accounting joins in M3b.
- **Contracts.** `shared/simulation.ts` defines the observer frame (date, clock state, events since a cursor, counters, a marker per population group with its polity's id, kind, era and lineage, lineage names, the largest polities, living settlements, a summary, the civilization list, a region's details with its polity's knowledge, research, map, reach, stability and last decision; protocol 8), era names, the study's knowledge report, the region map (a separate versioned contract: cell → region as little-endian uint16 plus per-region summaries), controls, event types and the host–worker messages. Event text templates live in the browser-side observer data module `src/observer/events.ts`; a test fails if an event type lacks one.
- **Observer.** The lab polls `GET /api/simulation/frame` with a cursor, every 250 ms while playing and every second while paused; each request carries a sequence number and an older response never replaces a newer one, and frames of another world are ignored. Controls go to `POST /api/simulation/control` with the same cursor, so events a control causes are not skipped. The browser never imports `src/simulation`. Simulation marks (peoples' territories — a world-sized image, one pixel per cell, coloured by polity, descent or era and outlined, scaled to the camera — region borders, polity markers coloured by era from `src/observer/palettes.ts`, circles for bands and squares for civilizations, villages, and capitals as stars at every zoom) are drawn on a transparent overlay canvas stacked on the map, in the same camera, so observer frames redraw them without repainting the terrain and geography pixels stay independent of the simulation.
- **Headless study.** `npm run study:history` generates each seed's world through the lab's path (generate → encode → worker validation → regions) and drives the same worker through `server/simulation-host.ts`, writing per-century stats, the yearly population series, the knowledge report (firsts, eras, where Agriculture began), the event log, per-system timing, the story-health and acceptance tables and SVG charts under `.chronicle/studies/`. `scripts/review-screenshots.ts` captures the running lab at chosen years for review packages.
- **Development reloads.** `src/simulation/**/*` is in nodemon's watch list; a source-edit regression proves an edit there restarts the host and the next frame comes from a fresh year-0 simulation. Until slice P, a host restart or another seed resets the simulation to year 0 and the lab says so.

## Seeded geography and bounded detail delivery

The browser page is the seeded annual-climate world. `src/world/generation/` contains deterministic noise, continent/island elevation, climate, hydrology, sparse resource sites and encoding. The worker is the only runtime application layer importing generation. Browser, renderer and HTTP imports of this directory are rejected by Biome and exercised by negative architecture tests. The directory and vendored runtime are watched; climate-only and vendor-only source-edit regressions verify that changes replace workers and invalidate cached generation at the same proxy origin. Browser, renderer, shared, HTTP and unrelated core modules also cannot import the vendored runtime directly.

World generation protocol 5 is defined in `shared/generated-world.ts`: settings (seed plus standard/large resolution), generator version, immutable geography identity, a manifest, and 128 × 128 tiles. Numeric columns carry elevation in metres, temperature in tenths °C, moisture in thousandths, biome codes, resource codes (zero means no site), and fertility scores (0–100). Manifest and tile validators check shape, lengths, ranges, water/elevation consistency, identity, tile coordinates and summary accounting before publication/use. Row-major cell IDs remain stable within an identity. There are no province, country, settlement or occupation fields in this geographic contract.

Both presets cover 510 million km² including ocean. Standard has 512 × 256 cells; large has 1,024 × 512. Equal-area cylindrical latitude is `asin(1 − 2v)`, with horizontal wrapping and bounded poles. Cell areas are uniform, while apparent map lengths and shapes are distorted near the poles. Future travel mechanics require geodesic or explicit land-travel distances; rendered cell edges are not uniform ground lengths. Resolution is not a separate planet area setting in this preview.

Generator 6 uses a pinned, patched [Mindwerks Platec](https://github.com/Mindwerks/plate-tectonics) C++ core compiled with Emscripten 6.0.5 to a committed WebAssembly/ESM artifact under `vendor/platec/`. A fresh module instance owns each asynchronous job; raw heights are copied and validated before destruction. The WASM heap is capped at 128 MiB and simulation at 2,500 steps, inside the existing disposable worker deadline. This heap cap is separate from V8/process memory. Complete source, licenses, local patches, compiler options and checksums are retained; `npm run check:tectonics` rejects source/artifact drift, and explicit `npm run build:tectonics` rebuilds it. Ordinary installation and startup need only Node and npm.

Both atlas presets refine one fixed 512 × 256 tectonic base, preserving geography across resolution changes. Initial continental noise uses all 32 seed bits and a larger domain to support several crust cores before movement/collision. The adapter treats the toroidal model as an elevation donor: it chooses an ocean-heavy cut and trims about 1% of donor rows from each side, then samples bounded latitude while keeping longitude periodic. A separately interpolated donor land/water mask preserves straits during elevation refinement. The outer 3% of atlas rows fade into separate polar oceans. Dimensionless crust thickness becomes bounded metre elevations with deterministic local relief. Broad lowlands and coastal relief grading feed the existing climate pipeline. This is an artistic tectonic approximation, not spherical geological or drainage simulation.

The climate is a reproducible annual approximation: a symmetric latitude baseline and elevation cooling, broad moisture bands, ocean replenishment, finite wind transport, moisture loss on rising slopes, and a terrain-weighted crosswind averaging of annual moisture. The crosswind step prevents independent latitude rows from producing narrow humidity stripes downstream of small coastal differences. Biomes follow those values rather than per-island quotas. Sea ice is a cold-water classification; snow is a land biome. Seasonal water balance, weather, ocean currents and calibrated geology are not modeled; VISION.md keeps geography annual, and seasons enter only through the simulation's harvest calendar. Resource sites use suitable terrain and sparse spacing across the longitude seam, with independent rarity choices; extraction remains catalog metadata only. Generator 6 then appends tin (a few upland provinces, fewer than half of copper) and oil (a few lowland basins) with their own seeded streams, only on land cells without a site (`src/world/generation/resource-clusters.ts`).

Hydrology runs after climate and before final lake biomes/resources. `src/world/generation/hydrology.ts` uses deterministic Priority-Flood over D4 neighbors (horizontal wrapping, bounded poles), routes each lake to one outlet or closed root, and accumulates moisture-weighted cell area in topological order. Ocean is negative-bed water connected to polar boundaries; enclosed negative-bed water remains at level zero. New lakes are supply-limited, at most 20 m deep and 100,000 km²; deep or oversized depressions retain a bounded pond near their minimum instead of flooding the accepted continents. All passes are bounded (48), elevation remains unchanged, and unsupported configurations fail explicitly. Generator 6 ([G1](features/g1.md)) records each pass's sink state: a pit beside a spill path at the same level (or two equal minima) could alternate forever between a dry river terminal and an unsupplied pond, so a repeated state fixes the oscillating cells at the highest level they reached. Such fixed ponds can be small closed lakes without supply. A converged pond that would leak into a lower neighbour outside it, other than its outlet (rejected by the water contract), has its sinks released and drains through that neighbour. Worlds that never repeat a state or leak are unchanged. This static retention approximation does not simulate erosion, groundwater or seasonal discharge.

`shared/world-hydrology.ts` validates the authoritative sparse river graph, lake membership/levels/outlets, and explicit dry sinks. Ordinary river channels require accumulated runoff of at least 5,000 area-index units. Weaker lake outflows retain their full downstream path to ocean, another lake or a registered dry terminal with incoming flow below that threshold. The contract rejects broken paths, uphill edges, cycles, contradictory lake geometry, impossible incoming/terminal flow and submerged land resources. The renderer and inspector consume this same graph. Open lakes and rivers expose mapped freshwater access; closed-lake salinity is not inferred. Lake surface shading uses water level while inspection preserves bed elevation. The Rivers toggle affects the Biomes layer; temperature/moisture views retain literal climate colors. `src/renderer/river-paths.ts` derives connected reaches once from the validated graph, retaining every edge and exact fork/water-boundary positions. Quadratic bends stay within routed cells; longitude is unwrapped before smoothing. Reach runoff controls width and zoom-dependent visibility, keeping larger rivers at overview and revealing small streams at detail. This is presentation only: generation identity, cell picking and water facts are unchanged.

The worker validates and pre-encodes a full-resolution terrain surface, a 256 × 128 sampled climate overview and all detail tiles into an immutable bundle. The terrain surface packs signed little-endian 16-bit elevation followed by an unsigned 8-bit biome for each row-major cell, base64 encoded in JSON. It preserves narrow coasts and small islands at overview zoom without fetching every tile. Surface validation checks exact dimensions, byte length, value ranges, water/elevation consistency, full biome counts and agreement with sampled terrain values. Each received detail tile must also match the surface elevation and biome for every cell. Private decoded validation data is retained weakly per manifest, avoiding repeated whole-world decoding for each tile. `server/generated-world-store.ts` retains at most two bundles, including unfinished jobs. It shares in-flight generation for identical settings, evicts only completed least-recently-used entries, removes failed entries for retry, and cancels unfinished work only after its last waiting observer disconnects. Closing the app cancels unfinished generation and clears the cache. This is a disposable geography cache, not saved user worlds. The main thread unpacks bounded bundle strings and validates the manifest; generation and tile encoding stay in workers.

The browser receives the full terrain surface and sampled climate overview first and requests exact detail for visible tiles or selected cells. Its client caps requests at four concurrently and its data cache at sixteen tiles. Current viewport tiles are protected from eviction by late offscreen responses; protection moves with the view and clears at overview. The biome renderer uses one full-resolution terrain plate and world-coordinate wave, vegetation, dune and crag marks at several zoom levels. It samples relief across world/tile boundaries and keeps biome terrain identical as detail arrives. Climate layers use their literal legend colors, with detail textures bounded to retained tiles and cleared when changing layer. World replacement cancels the prior client; revision checks prevent late data from changing selection or replacing a newer world. Failed replacement keeps the displayed world; failed detail keeps the overview and requires an explicit retry. Cell inspection reads a full-resolution tile even when the map is showing an overview. Pan, zoom and inspection are observer views, not world mutations.

Fertility is generated after geography, climate, hydrology and resources, without modifying those fields. `shared/fertility.ts` is a pure game model shared by worker generation, transport validation and exact cell inspection. Its context indexes lake levels and freshwater/river proximity once per surface. Regional slopes use neighboring surface elevations and spherical distances in the equal-area projection, with wrapped longitude and bounded poles. This is coarse regional relief, not local field slope. Estimated soil classes use terrain, climate and nearby rivers; actual soil chemistry, geology and crop requirements are not known. Water is excluded. Rounded warmth, moisture, soil, slope and drainage factors multiply into an integer score, so the inspector explains the transported value exactly. Freshwater proximity is descriptive and grants no irrigation. Manifest samples and every tile score are checked against this same rule. Only one extra numeric column is transported; explanatory factors are computed for inspected cells. The full-resolution terrain encoding and water graph remain unchanged. Generator 6 / protocol 5 invalidate older generated cache identities.

Resource sites are sparse: most cells have none, and a site's presence is neither an inventory nor an extraction rate. Extraction requirements are catalog metadata displayed for review, not a claim that any actor knows a technology or can produce goods. Research, discovery, production, labor and stocks need later contracts.

## Growth and dependency decisions

Chronicle is intended to become a substantial simulation project. Small slices govern delivery and review; they do not limit the product's architecture or expected complexity. Plan for large world datasets, many active and archived entities, long histories, and multiple independent worlds. Evaluate memory residency, generation and stepping costs, history retention, simultaneous saves, and reconnect payloads with representative workloads as those capabilities develop. The current geography workload and conservative runtime limits are evidence about the present workload only, not eventual capacity targets.

Keep one modular application now, with clear boundaries between world rules, transport, HTTP, compute ownership, rendering, and persistence. Those boundaries must allow later changes to process placement, server topology, and storage when known requirements or measurements justify them. Changes still require explicit contracts, implementation, migration planning, and verification; modularity does not make a database or distributed-runtime migration automatic. Evaluate additional runtime services by the requirements they satisfy and their operating costs, rather than assuming either that the project is too small to need them or that growth alone requires them immediately.

Use established libraries and tools for infrastructure where they provide a concrete benefit. The user authorizes necessary local package/tool installation for current work and future growth without an extra approval step. For adoption, check purpose, maintenance, license, Node/TypeScript and browser compatibility where relevant, operational requirements, and the cost of integration or replacement. Verify actual behavior with the installed version, pin direct package versions, update the lockfile, and reproduce installation with `npm ci`. Keep README accurate and preserve `npm ci`, then `npm start`, as the everyday setup and launch path.

`npm run check:architecture`, included in `npm run check`, runs the targeted Biome rules over `src`, `shared`, `server`, `scripts`, and the authored `vendor/platec/runtime.ts` helper. The configured boundaries keep shared contracts independent of application layers; world-core modules (`src/world`, `src/simulation`, and the reserved `src/fixtures`) independent of rendering, React, and host infrastructure, with only world generation and the worker importing `src/world/generation`; renderer and browser code out of host computation; HTTP modules out of direct world-core execution; and worker handlers out of HTTP orchestration. Node module imports are rejected in the browser, renderer, shared contracts, world core and authored vendor helper. That helper may import only its local generated `platec.mjs` module; it cannot depend on Chronicle application layers. Generated C++/ESM files remain outside Biome and are covered by artifact-integrity checks. Import cycles, including type-only cycles, and undeclared package dependencies are also checked. Formatting and general style rules are not enabled by this configuration. [Configured rules](../biome.json), [Biome import restrictions](https://biomejs.dev/linter/rules/no-restricted-imports/javascript/), [cycle checking](https://biomejs.dev/linter/rules/no-import-cycles/javascript/)

Runtime modules also reject development-only package imports; composition scripts retain permission to load development tools such as Vite. These are static import checks, not complete runtime isolation. Literal import paths can be checked, but computed module names, worker URLs, access to browser/Node globals, and architectural intent still need review and appropriate tests. Update the rules when adding layers or import conventions, and retain independent review plus headless, browser, and process tests. Passing this check alone does not establish deterministic simulation or valid save/lifecycle behavior.

## Transport and capacity boundaries

Map endpoints have versioned contracts and use `Cache-Control: no-store` for HTTP responses:

| Endpoint | Payload | Browser use |
|---|---|---|
| `GET /api/world` | Generated-world protocol-5 manifest and overview | Requested for each displayed seed/resolution |
| `GET /api/world/tile` | Generated-world protocol-5 exact detail tile | Requested as needed by the view and cell inspection |
| `GET /api/simulation/frame` | Simulation protocol-4 observer frame for a world (`seed`, `size`, `cursor`, optional `inspect` region) | Polled while the lab is open |
| `GET /api/simulation/regions` | Simulation protocol-4 region map | Requested once per displayed world |
| `POST /api/simulation/control` | An observer control (play, pause, step, speed, run to year, reset); returns the frame | Time controls |

`/api/health` and `/api/ready` complete the API. Wrong methods on these routes return 405; other `/api` paths return 404. Simulation routes have their own admission limit (`CHRONICLE_SIMULATION_REQUESTS`, default 16 in flight), separate from map responses.

Workers construct geography, validate the matching contract, and serialize its JSON. The browser checks the shared structural and semantic contract before rendering. Invalid replacement data or failed requests preserve the last valid map. Generated-world manifests are capped at **4 MiB**, detail tiles at **512 KiB**, and worker bundles at **20 MiB**; the browser does not fetch the complete bundle. There are no saved-world migrations in this stateless lab. Future persistence ([VISION.md](VISION.md) slice P) versions its state separately with `SAVE_FORMAT_VERSION`; during VISION.md's run a save from an older save format is refused with a clear message and kept on disk, and migrations are required only from the first save format the user accepts.

All map endpoints share one pool: two workers, or one when only one processor is available, with four waiting jobs and a twenty-second deadline that includes queue time (configurable up to twenty-five seconds, below the thirty-second browser request deadline). Total admitted map responses across the routes are bounded to worker count plus queue allowance, with admission retained until the response finishes or closes. This also constrains work retained for slow clients after computation completes. Generated-world cache admission also limits simultaneous uncached seeds to two. Configuration is validated on startup; defaults and allowed ranges are recorded in README.

Request parsing, sockets, deadlines, and compute admission have explicit limits. Overload and timeouts return retryable failures. Disconnect cancels disposable geography work; worker failure returns an error and does not fall back to computing on the HTTP thread. Structured logs and server-generated request IDs support diagnosis. `/api/health` establishes HTTP responsiveness; `/api/ready` reports worker/admission diagnostics and returns 503 when busy or unavailable. Before announcing readiness, startup submits one uncounted probe job through the real worker. It proves that the worker's module graph (generation, the Platec loader and encoding) loads and that a job round-trips, without generating a world; Platec's WebAssembly is instantiated per generation and is covered by `check:tectonics` and the real-worker tests.

These are conservative engineering defaults. Worker heap limits and payload bounds are not a total process-memory guarantee. `npm run bench:world` measures the large default world's generation, delivery, payloads, event-loop delay and memory through the real application and workers; [Fertility 01](features/fertility-01.md) records the current results. One immutable world does not establish simultaneous-world capacity or simulation speed. Actual measurements and checks belong in the relevant feature brief.

## Remote access and next action

The host currently binds to loopback only. The PC must remain awake and the process running for the host or remote access to work. Before allowing access from other PCs, define authenticated sessions, per-world authorization, TLS, bounded subscriptions, and session revocation. Unattended startup and OS service management need their own scoped implementation; Docker is not a prerequisite.

The seeded generated world is the only browser page; its geography is visually accepted. Civilization work follows [VISION.md](VISION.md); its architecture section defines the dedicated simulation worker, its `shared/` contracts, determinism and world-instance identity. The removed runtime on `archive/civilization-v1` is reference only, and its contracts are not commitments. Any future mutable world built on this geography needs its own explicit, versioned contracts: the geography's seed/settings/version identity stays distinct from any future persistent world-instance identity. Authentication, remote access and unattended hosting remain separate work before opening access to other PCs.
