# Backend foundation: decisions and evidence

Researched 9 September 2026 against Node **24.20.0** and the package versions below. This report supports [Backend 02](features/backend-02.md); its implementation checklist, actual verification results, revision, and review status live in that brief. [ARCHITECTURE.md](ARCHITECTURE.md) records the current architecture and [README](../README.md) owns runnable commands. Recommendations below are Chronicle engineering decisions inferred from primary sources, not vendor guarantees about this workload.

## Requirements and the useful boundary now

Each person has an independent world. All generation and simulation run on the user's PC; browsers render the atlas and send observer controls. Worlds do not interact. A returning person must find their world again, and another tab must attach to the same authority. On departure, pause and save; on return, restore and resume a previously running world. Preserve manual pause and perform **no offline catch-up**. The PC must be awake and the host running for work or remote access to occur. These requirements come from the confirmed hosting decision and specification sections 5 and 13.

Backend 01 established a stateless terrain endpoint and browser failure handling. The authorized Backend 02 scope now adds a maintainable HTTP service, bounded background computation, shared transport validation, a standalone built-app server, operational conventions, and reproducible load evidence. These components serve the real accepted terrain fixture today. They do not establish procedural generation, simulation steps, persistent world identity, accounts, save/load, remote deployment, or a scheduler for resident worlds.

The baseline package choices are **Fastify 5.12.3**, **@fastify/static 10.1.3**, **Piscina 5.3.2**, and **TypeBox 1.3.30**, alongside the existing React, TypeScript, and Vite application. Exact published metadata was checked through the npm registry; the committed lockfile identifies the installed dependency graph. Source tags can differ from package metadata: Piscina's `v5.3.2` source manifest still reports `5.3.1`. Do not infer installed versions from that file. [Fastify package](https://registry.npmjs.org/fastify/5.12.3), [static plugin package](https://registry.npmjs.org/@fastify%2Fstatic/10.1.3), [Piscina package](https://registry.npmjs.org/piscina/5.3.2), [TypeBox package](https://registry.npmjs.org/typebox/1.3.30), [Piscina tagged manifest](https://raw.githubusercontent.com/piscinajs/piscina/v5.3.2/package.json)

## HTTP framework and shared contracts

| Option | Fit for Chronicle |
|---|---|
| Native Node HTTP | Appropriate for the original two-route fixture. Stable and dependency-free, but routing, errors, validation integration, logging, request limits, and lifecycle conventions become application maintenance. |
| Fastify | Selected. Schema support, hooks, request logging, and encapsulated plugins provide conventions that the authorized baseline immediately uses. |
| Express | Viable and familiar routing/middleware. Chronicle would still assemble more of its validation, logging, and lifecycle conventions separately. |
| Nest | Useful when its modules, dependency injection, and application structure solve an established organizational need. That structure is unnecessary for this repository's current service. |

These are scope and maintenance judgments, not a claim that Express or native HTTP cannot scale. Node documents HTTP as a low-level streaming interface; Express documents route handlers; Nest supplies architecture above Express or Fastify. Fastify's benefit here is the selected facilities, not a synthetic requests-per-second ranking. [Node HTTP](https://nodejs.org/docs/latest-v24.x/api/http.html), [Express routing](https://expressjs.com/en/starter/basic-routing/), [Nest introduction](https://docs.nestjs.com/), [Fastify schema support](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)

TypeBox supplies runtime JSON schemas with TypeScript type inference. The same transport definition belongs in a browser-independent module consumed by the worker and client. Structural checks cover the protocol, field types, dimensions, and bounded arrays; semantic checks still establish cell counts, finite values, stable IDs, and valid province references. A schema cannot establish every world invariant. Invalid data is rejected before rendering; the last valid map survives failed replacement. Schemas are trusted application code, never uploaded definitions. [TypeBox documentation](https://github.com/sinclairzx81/typebox), [Fastify validation guidance](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)

Preserve `GET /api/terrain` and `{ protocolVersion: 1, world }`. Construction, validation, and JSON serialization move together into the worker; returning a ready JSON string avoids moving serialization back onto HTTP handling. This response path must explicitly validate before sending: Fastify's response serializer alone is not an invariant check. Request IDs and structured logs connect failures to requests; clients receive bounded error envelopes without internal stacks. Health and readiness have separate meanings: a responding process is not necessarily ready to run its terrain worker. [Fastify logging](https://fastify.dev/docs/latest/Reference/Logging/), [Fastify server lifecycle](https://fastify.dev/docs/latest/Reference/Server/)

## CPU execution, limits, and ownership

Synchronous CPU work occupies the thread executing it, even inside an `async` function. Node recommends worker threads for CPU-intensive JavaScript and pooling workers to amortize startup. Child processes are an alternative when stronger process separation or another runtime becomes necessary; they introduce separate process memory and IPC management. Neither option proves a particular speedup. Keep the simulation core independent so execution placement remains changeable. [Node 24.20.0 workers](https://raw.githubusercontent.com/nodejs/node/v24.20.0/doc/api/worker_threads.md), [Node child processes](https://raw.githubusercontent.com/nodejs/node/v24.20.0/doc/api/child_process.md)

Piscina provides persistent workers, queue limits, task cancellation, and shutdown primitives. Configure these explicitly: its default queue is unlimited. A cancelled running task stops its worker, so the current pool is for **disposable fixture/generation jobs** whose inputs can reproduce the result. It is not the owner of uncheckpointed long-lived worlds. Workers must finish their asynchronous work before returning. [Piscina 5.3.2 API and lifecycle](https://raw.githubusercontent.com/piscinajs/piscina/v5.3.2/README.md)

Backend 02 starts with conservative application defaults:

| Resource | Initial bound and purpose |
|---|---|
| Workers | Two; one on a single-core host. Keep HTTP and browser resource needs in view. |
| Waiting jobs | Four. Excess demand receives an explicit retryable response. |
| Job deadline | Eight seconds from admission, including queue time. |
| Admitted terrain responses | Worker count plus queue allowance, retained through response closure. Finished computation must not permit unbounded retained responses. |
| Transport | At most 100,000 cells and 8 MiB serialized JSON. These are independent limits. |

The limits bound specific queues and payloads; they are not a total process-memory guarantee or a simultaneous-user promise. Worker heaps, strings, validation structures, response buffers, and browser objects add overhead. Slow clients matter after computation finishes. Deadline expiry and disconnect must release disposable work; worker failures must produce errors and recovery, never synchronous fallback. Shutdown stops admission and closes sockets and workers within a bounded interval.

A future resident-world scheduler requires a separate contract: one ordered mutation authority per world, fair bounded work batches, explicit pause acknowledgements, and bounded output queues. Connections do not allocate simulations. Reset/incarnation IDs must invalidate stale jobs and messages. Parallel worlds must preserve each world's deterministic result. Cancellation of a browser request must not automatically destroy the only copy of mutable world state.

## Development, built serving, and evidence

Development keeps `npm ci`, then `npm start`: Vite and Fastify share one Node process, with CPU jobs in worker threads. Development assets retain Vite hot updates. The built path serves `dist` and API routes through Fastify and `@fastify/static`, without a Vite runtime. Static routing must not turn unknown API requests into successful HTML responses. The plugin documents Fastify compatibility and static-file behavior; Vite explicitly reserves its preview server for local preview, not production serving. [Static plugin 10.1.3](https://github.com/fastify/fastify-static/tree/v10.1.3), [Vite deployment guidance](https://vite.dev/guide/static-deploy.html)

This is an executable foundation for eventual hosting, not a network deployment. Keep loopback binding. Docker is unnecessary for one PC process; a later unattended-host slice can use the OS service manager with a stable working/data directory, restart policy, logs, and graceful shutdown. Linux systemd supports direct executable services. Choosing the target operating systems precedes writing their service installation instructions. [systemd service documentation](https://raw.githubusercontent.com/systemd/systemd/main/man/systemd.service.xml)

Record measurements with hardware, Node version, build mode, worker/queue configuration, fixture size, concurrency, response bytes, successful/rejected/timed-out requests, latency percentiles, and memory observations. Health latency while controlled CPU work is still running establishes event-loop isolation. A fixture benchmark measures the fixture pipeline; a labelled synthetic CPU test isolates scheduling behavior. Neither establishes centuries of simulation throughput. Actual results belong in the active brief, and failures must remain represented rather than disappearing from successful-request averages.

## Storage decision and why installation waits

**Choose local SQLite for the first persistent-world slice; do not add a database in Backend 02.** The current fixture has no user-specific progress to protect. Saving copies or adding empty tables would not verify meaningful continuation. Persistence should arrive when independent world identity and meaningful state exist, before users accumulate progress, rather than waiting for every simulation subsystem.

SQLite fits application-owned data on a local device, including an application server answering browsers. PostgreSQL supplies a separate database server and richer concurrent access machinery, but no measured Chronicle requirement currently justifies that service. Revisit PostgreSQL if multiple hosts or substantial simultaneous writers become necessary. SQLite permits one writer per file; independent-world files are an available later partition, not a reason to start with multiple storage systems. [SQLite selection guidance](https://sqlite.org/whentouse.html), [PostgreSQL architecture](https://www.postgresql.org/docs/18/tutorial-arch.html), [PostgreSQL concurrency](https://www.postgresql.org/docs/18/mvcc-intro.html)

The first store can hold world metadata, versioned immutable checkpoint payloads, and a transactionally updated current-checkpoint reference. Shared TypeScript remains authoritative for world rules; avoid designing relational tables for mechanics that do not exist. Measure representative snapshot size, serialization cost, save latency, and retention before choosing compression or incremental storage.

Node **24.20.0** documents `node:sqlite` as **Stability 1.2, release candidate**, promoted in 24.15.0. `DatabaseSync` and `StatementSync` are synchronous; `backup()` returns a Promise. The installed runtime and an in-memory query report **SQLite 3.53.4**. Prefer this built-in API behind a small storage boundary when persistence starts, with its RC status recorded and substantial work outside request handling. It was inspected, not wired into Chronicle storage. [Exact Node SQLite documentation](https://raw.githubusercontent.com/nodejs/node/v24.20.0/doc/api/sqlite.md)

`better-sqlite3` **13.0.3**, released 5 August 2026, is a viable alternative if a required capability or stability decision warrants it. It supports Node `>=22`; version 13 moved to Node-API and bundled platform prebuilds. Unsupported platforms can still require compilation, so target-PC installation must be checked. Its synchronous API does not itself remove HTTP blocking. No driver is installed for Chronicle saves yet. [13.0.3 release](https://github.com/WiseLibs/better-sqlite3/releases/tag/v13.0.3), [13.0.0 changes](https://github.com/WiseLibs/better-sqlite3/releases/tag/v13.0.0), [versioned package metadata](https://raw.githubusercontent.com/WiseLibs/better-sqlite3/v13.0.3/package.json)

## Persistence and lifecycle acceptance contract

The first implementation must cover the following together:

1. **Consistent checkpoints.** Save only at a completed step. Preserve versions, seed/configuration, RNG streams, tick/date, stable IDs, geography, active and archived entities, in-flight work, scheduled events, and required history. The renderer's view is insufficient. Snapshot and metadata commit together; a stale save cannot replace a newer world incarnation.
2. **Durable acknowledgement.** Use local-disk WAL with `synchronous=FULL` for acknowledged saves intended to survive power loss; `NORMAL` can roll back recent commits after power or OS failure. Enable foreign keys and bound lock waits. WAL permits readers alongside a writer, but is unsuitable for a shared network filesystem. The installed SQLite is newer than 3.51.3, which fixed the documented WAL-reset bug. [SQLite synchronization](https://sqlite.org/pragma.html#pragma_synchronous), [WAL guarantees and limitations](https://sqlite.org/wal.html)
3. **Failure recovery.** Announce “saved” after durable commit. On failure, retain recoverable in-memory state, remain paused, and preserve the last good checkpoint. Define periodic checkpointing and the acceptable recovery gap: departure-only saving cannot protect unexpected host failure. Signals cannot guarantee a final save after `SIGKILL` or power loss. [Node process signals](https://raw.githubusercontent.com/nodejs/node/v24.20.0/doc/api/process.md)
4. **Departure and return.** Track the last relevant connection with host-side expiry and a specified reconnect grace period. Browser unload events are unreliable. Pause at a boundary, save, then release compute. Preserve manual pause, reset the playback schedule on resume, and never derive offline simulation steps from elapsed wall time. [Browser departure limitations](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event)
5. **Safe loading and migration.** Validate a candidate before replacing a live world. Version the storage schema separately from save/rules versions; SQLite's application-controlled `user_version` does not perform migrations. Reject unsupported newer saves, retain pre-migration recovery, and bound imported and decompressed data. Host authorization determines ownership, not imported metadata. [SQLite application version](https://sqlite.org/pragma.html#pragma_user_version)
6. **Backup and authority.** Use SQLite's online backup API and test restoration; copying only a live `.db` can omit committed WAL state. Keep recoverable backups separately. Also prevent two host processes from owning the same persistent world: database transaction locking does not prevent two simulations from advancing it independently. [SQLite backups](https://sqlite.org/backup.html), [WAL file state](https://sqlite.org/wal.html)

## Remote-access gate and next narrow slice

Before access from other PCs, add TLS, authenticated sessions, ownership checks on every world read/control/export/subscription, and bounded connection/message traffic. World IDs identify resources; they do not grant permission. If WebSockets are chosen, validate allowed origins, authorize messages, and revoke or expire live sessions. The baseline does not select or implement that transport or an account provider. [OWASP authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [OWASP WebSocket guidance](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html)

After Backend 02 review, propose one world-identity and recovery slice using two explicitly labelled local test owners and real shared world data: distinct world IDs, independent reset/replacement, second-tab attachment, and restart restoration. Introduce SQLite there when the state has meaning. Do not invent tick counters or simulated populations to make persistence tests pass. Deterministic save/load continuation and completed-step pause become acceptance requirements as soon as actual shared stepping exists. Test disk failure, interrupted writes, incompatible loads, backup restoration, and reconnect races against that implementation. Remote access and a full resident-world scheduler remain subsequent scoped decisions.
